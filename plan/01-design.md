# 01 模型服务目标与边界

## 1. 用户可见能力

1. 登记不同模型 ID、runtime、能力和资产集合，校验文件、版本、挂载与预算。
2. 将模型资产只读映射到受控后端，加载后验证真实实例和就绪状态。
3. 根据请求切换模型；持有有效租约时保护正在执行的计算，停止确认后释放预算。
4. 提供模型列表、状态、加载/卸载、推理访问和故障恢复接口。
5. 拒绝超出设备实测输入 envelope 的请求；公开排队、超时和资源未知的确定错误。

当前源码为固定四个 llama.cpp 模型及三类推理 API。拟议增量是动态模型注册、多资产、多 runtime 和通用控制协议。
本项目不以支持某一部影片、某个视频模型组合或某种分析质量作为完成定义。

## 2. 模块所有权

| 模块 | SelfModelSwitch 职责 |
|---|---|
| config/contracts | 动态模型、runtime、asset、envelope 与协议类型 |
| registry/scheduler/request_queue | 模型状态、请求租约、通用会话、资源账本与切换 |
| backend_router / backend adapters | 白名单加载、执行、取消、卸载；按模型协议适配 |
| model_runner/process_observer | 受管容器身份、受限启动参数、独立停止证据 |
| storage_monitor | 模型盘与模型资产校验 |
| gateway/app | 兼容 API 与通用模型操作接口 |
| deploy/acceptance | 模型服务候选、软件/设备/运维证据及发布门禁 |

Torch/ORT 等模型依赖留在对应 worker 镜像，不进入调度进程依赖锁。
模型 adapter 只处理模型输入输出和执行终结；视频阶段、字幕、人物实体、报告模板不进入 adapter。

## 3. 独立视频项目边界

视频项目拥有媒体解码/编码、切片、阶段编排、SQLite、检查点、人物和声线 title、音频/波形、人工关联和报告。
它使用模型服务 API，不读写 scheduler 的 registry、不接触 Docker 控制端口、不调用未受控后端。
SelfModelSwitch 不接受 job_id、stage_id、电影 profile 或分析质量 policy 作为资源调度契约。
通用会话只携带客户端身份、model_id、输入规格及不透明追踪 ID。

同机的 FFmpeg/媒体内存由视频项目限流与预留；模型服务依据实际 MemAvailable 准入。
两个项目的组合内存和吞吐由视频集成验收负责，模型服务单项通过不能证明组合可用。
首版视频项目把重媒体处理和模型计算分开执行；未来如需并行，独立测量并修订集成约束。

## 4. 范围约束

单机 Linux、单调度进程、单 worker；本机访问。模型与设备可配置，不写死 Thor/Orin 或 MOSS/Qwen 型号。
首版新增通用会话选择单模型独占；既有接口并发/预加载行为需保留原配置约束，不静默改变。
不提供业务工作流、通用 shell 执行、公网、多租户、自动模型下载或驱动升级。
新类型和具体模型支持范围必须由 M00/M01 验证后登记，不把“支持 worker”描述为任意模型即插即用。
